# 실무 작업공간 데이터와 판단 기준

## 사용 흐름

첫 화면은 우선 확인할 상품과 기간별 판매량이다. `전체 상품`에서 한 상품을 선택해 판매 추이와 입력한 재고·원가를 확인하고, 할인·매입 시나리오를 비교해 판단 이유를 저장한다. 자사 작업공간에서는 실제 조치 실행일과 이후 판매 자료를 추가해 전후 7일 판매 수량·매출·매출총이익을 기술적으로 비교할 수 있다. 실행 전날과 실행 후 7일째의 재고를 각각 입력했다면 재고 변화도 표시한다. 입력값은 날짜별로 보존된다. 전후 차이를 조치의 인과 효과로 해석하지 않는다.

## H&M 시연 자료

사용자가 제공한 Kaggle H&M ZIP에서 상품 105,542종, 고객 1,371,980명, 거래 31,788,324행을 확인했다. `backend/scripts/import_hm.py`는 고객 ID를 DB에 저장하지 않고 여성복 세 섹션(`Womens Everyday Collection`, `Womens Tailoring`, `Womens Jackets`)의 2019·2020년 7~9월 상위 상품 각 50종 합집합만 적재한다. 현재 결과는 상품 279종, 상품×일자×채널 85,856행이다. 이 범위는 전체 H&M 판매를 대표하는 표본이 아니라 **의도적으로 선정한 시연 상품군**이다. 데이터 기준일은 2020-09-22다.

거래 한 행을 상품 판매 1개로 세며, 동일한 거래 행의 중복도 개별 구매로 센다. `price`는 원화가 확인되지 않은 정규화 값이므로 원화 매출에 사용하지 않는다. H&M 원본에는 재고, 원가, 발주일, 입고, 반품 사유, 실제 조치, 주문번호가 없다. 이 값은 프로그램이 추정해서 사실처럼 채우지 않는다. 고객 연관 상품 분석도 같은 주문의 동시 구매로 표현하지 않는다.

사용자가 제공한 `images.zip`과 선정 상품 ID를 비교해 279종 중 278종의 사진이 맞았다. 사진은 `frontend/public/hm_images/`에 로컬 추출했으며 `.gitignore`로 제외한다. 원본 이미지 ZIP과 CSV ZIP을 Git 저장소에 복사하지 않는다. 이미지가 없는 상품은 사진 없이 표시한다. 원본 데이터·이미지를 외부에 배포하기 전에는 [Kaggle 대회 규칙](https://www.kaggle.com/c/h-and-m-personalized-fashion-recommendations/rules)을 확인한다.

## 자사 파일 업로드

`오늘의 할 일`의 `자사 상품·판매 파일 연결`에서 두 파일을 함께 업로드한다. CSV(UTF-8, CP949) 또는 XLSX를 지원하며 파일당 15MB 한도다. 새 작업공간을 만들고 기존 작업공간은 변경하지 않는다. 올리기 전에 모든 SKU·날짜·수치를 검증한다.

- 상품 필수 열: `sku,name`
- 상품 선택 열: `category,section,stock_on_hand,inbound_units,lead_time_days,unit_price_krw,unit_cost_krw,reorderable,lifecycle`
- 판매 필수 열: `sku,sale_date,units_sold`
- 판매 선택 열: `revenue,gross_margin,channel`
- `lifecycle`: `regular`, `summer_clearance`, `fall_prelaunch`, `winter_carryover` 중 하나. 비워두면 미확인.

상품에 현재고를 넣는 경우 재고 기준일과 판매 파일의 마지막 날짜가 같아야 한다. 같은 상품·날짜·채널이 판매 파일 안에서 반복되면 수량과 금액을 합산한다. 이후 `내 결정 기록`에서 새 판매 파일을 올리면 같은 키만 교체하고 다른 기록은 보존한다. `sample_data/company_products_template.csv`와 `sample_data/company_sales_template.csv`를 형식 예시로 사용한다.

`모든 판매가 포함돼 있습니다` 확인란을 선택해야 빈 날짜를 0개 판매로 해석해 추세 판단과 전후 비교를 한다. 선택하지 않으면 판매 자료 확인 상태로 표시한다. 실제 회사 파일에서 고객명, 전화번호, 주소 등의 개인정보 열은 제거한다.

## 지표와 제한

- **최근 14일 판매 변화**: 기준일 포함 최근 14일 수량과 그 앞 14일 수량을 비교한다. 직전 수량이 5개 이상이고 최근 수량이 30% 이상 줄면 `판매 감소`로 검토한다. 감소 원인은 데이터만으로 단정하지 않는다.
- **재고 소진 예상일**: 기준일 현재고 ÷ 최근 14일 평균 판매 개수. 기준일이 맞는 재고가 없거나 판매가 0개면 계산하지 않는다. 판매 속도가 그대로 이어진다는 단순 가정이며, 행사·품절·계절 변화를 예측하지 않는다.
- **재고 위험**: 예상 소진일이 입력된 입고 소요일 이하인 경우 검토한다. 재발주 불가면 추가 매입을 제안하지 않는다.
- **시나리오 매출총이익**: 입력한 예상 판매 개수 × (원화 판매가 × (1 − 할인율) − 입력 원가). 재고가 부족하면 이익을 계산하지 않는다. H&M 원본 판매가나 실제 할인 효과를 근거로 사용하지 않는다.
- **전후 비교**: 자사 자료에서 실제 실행일과 완전한 전후 7일 판매 기록이 있을 때만 수량을 표시한다. 매출·매출총이익은 해당 기간의 모든 행에 실제 금액이 있을 때만 표시한다. 재고는 실행 전날·실행 후 7일째 각각 입력한 스냅샷이 있을 때만 표시한다. 대조군이 없어 인과 효과를 증명하지 않는다.
- **판매 미관측**: 기준일까지 판매가 한 번도 관측되지 않은 상품은 `정상`이 아니라 `판매 미관측`으로 표시하고 소진 예상일을 계산하지 않는다.
- **다음 시즌 기획**: 상품 종류의 전기 판매와 동일 SKU의 전년 판매를 참고한다. H&M 선정 상품군의 합계는 전체 회사나 전체 카테고리 수요가 아니며, 신상은 같은 SKU의 전년 기록이 없을 수 있다. 여름 잔여·가을 출시 전·작년 겨울 행사 상태는 MD 입력에만 따른다.

## H&M 운영 시뮬레이션 보기

H&M 작업공간에서는 `실제 판매만 보기`와 `운영 시뮬레이션 보기`를 나눈다. 시뮬레이션은 `sample_data/hm_operating_case/`의 50종만 대상으로 하며, `운영 시뮬레이션 자료 연결` 버튼(`POST /api/work/sim/import-sample`)으로 별도 `work_sim_*` 테이블에 저장한다. 자사 파일 업로드 경로를 쓰지 않는다. 가져올 때 관측 판매 일치, 수불식, 발주↔입고, 재발주 불가 규칙을 모두 검사하고, 하나라도 실패하면 저장하지 않는다.

판단 기준일은 2020-08-31로 고정한다. 8월 31일까지의 관측 판매와 가상 재고로 재고 위험·과잉·판매 변화를 계산한다. 9월 1~22일은 `이후 관측 판매`로 분리하고, 8월 31일의 가상 재고와 계획 입고로 공급할 수 없었던 수량을 `가상 정책상 공급 부족분`으로 표시한다. 이 값은 실제 H&M 품절이나 잃은 매출이 아니다. 판매는 `H&M 관측`, 재고·발주·원화 가격·원가·상품 상태는 `가상 운영 조건`, 판단과 매출총이익은 `시뮬레이션`으로 표시한다. 판단 기록은 저장 당시의 값과 출처를 스냅샷으로 보관한다. H&M 작업공간의 279종은 9월 판매가 반영된 표본이라는 편향을 화면에 계속 표시한다. 세부 규칙은 `sample_data/hm_operating_case/DATA_QA.md`에 있다.

이 버전은 로컬 포트폴리오 시연과 소규모 자사 파일 분석에 적합하다. 여러 MD의 동시 사용, 권한, 발주 시스템 연결, 이력별 원가와 재고 수불, 반품·취소 정산, 대규모 실시간 적재는 아직 지원하지 않는다.
