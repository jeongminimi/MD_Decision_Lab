# H&M 관측 판매 기반 가상 운영 사례 — 데이터 QA (v2)

> **이 폴더의 재고·발주·가격·원가는 모두 가상 시뮬레이션 값이다.** 실제 값은 H&M 거래 기록에서 집계한 일별 판매 수량(`units_sold_observed`)뿐이다. 재고 수불, 발주, 원화 판매가·원가, 시즌 상태는 H&M 원본에 없다. 관측 판매를 제약조건으로 삼아 아래 규칙으로 만든 값이다. 이 파일로 계산한 매출·이익과 공급 부족분은 **실제 H&M 실적·품절·잃은 매출이 아닌 시뮬레이션 값**이다.

## 1. 입력과 재실행

| 항목 | 값 |
|---|---|
| 판매 원천 | `backend/md_decision_lab.db`의 `work_datasets.kind='hm'` 작업공간(`H&M 실제 판매 · MD 시연`). `work_daily_sales`를 상품×일자로 합산(채널 1·2 합계) |
| DB 접근 | `sqlite3` 읽기 전용(`mode=ro`). 생성·검증 스크립트는 DB·프로그램 코드·원본 ZIP을 수정하지 않음 |
| 판단 기준일 | **2020-08-31 고정.** 상품 선정, 8/31 재고, 모든 발주는 이 날짜까지의 판매만 사용 |
| 수불 기간 | 2020-07-01 ~ 2020-09-22 (84일). 09-01~09-22는 **이후 관측 판매**로 분리 |
| 난수 시드 | `20200831` (버킷 안의 상품 순서 섞기에만 사용) |
| 생성 | `python sample_data/hm_operating_case/generate_hm_operating_case.py` (`MD_Decision_Lab/`에서 실행) |
| 검증 | `python sample_data/hm_operating_case/verify_hm_operating_case.py` → 종료 코드 0이면 통과 |
| 프로그램 연결 | 실무 작업공간 → H&M → `운영 시뮬레이션 보기` → `운영 시뮬레이션 자료 연결` (`POST /api/work/sim/import-sample`). 자사 업로드 경로를 쓰지 않음 |
| 저장소 포함 여부 | CSV 4개는 H&M Kaggle 대회 데이터(상품 ID·상품명·일별 판매)에서 나온 값이라 Git에 올리지 않는다(`.gitignore`). `backend/scripts/import_hm.py`로 로컬 DB를 만든 뒤 생성 스크립트로 다시 만든다. CSV가 없으면 `backend/tests/test_hm_simulation.py`는 건너뛴다 |

`hm_weekly_sales.py`는 `article_id`를 `int32`로 읽기 때문에 앞자리 0이 사라진다. 선정 50종은 모두 `0`으로 시작하므로, 숫자로 읽으면 50종 모두 DB 상품 ID와 연결되지 않는다. 이 폴더의 스크립트와 프로그램 가져오기는 SKU를 문자열로만 다룬다. 엑셀로 CSV를 열 때도 SKU 열을 텍스트로 지정해야 한다. 채널 번호의 온·오프라인 의미는 확인하지 않았으므로 합산만 했다.

## 2. v1 → v2 변경: 사후 정합 입고 제거

v1에는 9월 관측 판매가 가상 재고를 넘을 때 수불을 맞추려고 넣은 발주일 없는 `reconciliation_assumed` 입고가 20건(11,150개) 있었다. 이 입고는 8/31에 계획할 수 없었던 값이라 정상 발주·계획 입고·MD 조치처럼 보일 위험이 있어 v2에서 제거했다.

- 발주는 **8/31까지만** 낸다. 9월에는 새 발주가 없으며, 8/31 이전에 낸 발주만 예정대로 입고된다.
- 관측 판매가 가상 가용 재고를 넘으면 재고를 음수로 두거나 입고를 지어내지 않는다. 대신 아래 필드로 나눈다.

| 필드 | 의미 | 출처 |
|---|---|---|
| `units_sold_observed` | H&M 관측 판매 | H&M 관측 |
| `units_supplied_synthetic` | min(관측 판매, 기초재고 + 입고) — 가상 재고로 공급 가능한 수량 | 시뮬레이션 |
| `supply_shortfall_synthetic` | 관측 판매 − 공급 가능 수량 — **가상 정책상 공급 부족분** | 시뮬레이션 |
| `closing_stock_synthetic` | 기초재고 + 입고 − 공급 가능 수량 (≥ 0) | 가상 운영 조건 |
| `period` | `as_of_window`(7/1~8/31) 또는 `post_as_of_observed`(9/1~9/22) | — |

기준일 이전(`as_of_window`)에는 관측된 판매가 실제로 일어났으므로 공급 부족분이 0이 되도록 기초·초도 수량을 맞췄다(12종 보정, `assumption_reason`에 표시). 8/31 상태는 v1과 같다(8절 누출 검사).

**표본 편향:** DB의 279종은 `import_hm.py`가 2019·2020년 7월 1일~9월 22일 판매 상위 상품으로 고른 것이라 모집단 자체에 9월 판매가 반영돼 있다. 판매 미관측 4종도 "9월에 잘 팔려서 DB에 들어온 상품"이다. 이 폴더의 선정 규칙은 9월을 쓰지 않지만, 모집단의 편향은 제거할 수 없다. 프로그램 화면에도 같은 문구를 표시한다.

**가상 시즌 상태:** `fall_new_scenario` 14 · `summer_clearance_scenario` 7 · `winter_carryover_scenario` 6 · `unassigned` 23종이다. 모두 가상 운영 시나리오이며 실제 출시·행사 사실이 아니다. 관측 판매로 뒷받침되지 않는 23종에는 상태를 부여하지 않았다. 2020년 겨울 실적은 데이터 기간 밖이라 만들지 않았다.

## 6. 2020-08-31 판단 (프로그램의 `services/work_risk.py`와 같은 규칙)

판매 속도 = 최근 14일 판매 ÷ 14. 소진 예상일 = 8/31 가상 기말재고 ÷ 판매 속도. 판정 순서는 재고 0 → **판매 미관측** → 소진 위험(소진 예상일 ≤ 리드타임) → 과잉(≥ 60일) → 판매 감소 → 판매 증가 → 정상이다.

| 판단 | 수 | 대표 SKU | 최근14일 / 직전14일 | 8/31 재고 | 소진 예상 |
|---|---:|---|---|---:|---:|
| 소진 위험 | 17 | 0915526001 Nika vest (가을 신상, 가상) | 1,080 / 173 | 5 | 0.1일 (리드 28) |
| 재고 과다 | 15 | 0749699002 Chestnut strap top (여름 잔여, 가상) | 176 / 412 | 3,359 | 267.2일 |
| 판매 감소 | 3 | 0895002002 Steam smock top (여름 잔여, 가상) | 194 / 356 | 465 | 33.6일 |
| 판매 증가 | 3 | 0817354001 Biarritz | 290 / 204 | 877 | 42.3일 |
| 판매 미관측 | 4 | 0909370001 FF PI Haley dress | 0 / 0 | 840 | 계산 안 함 |
| 정상 | 8 | 0733097001 Saga body | 181 / 191 | 399 | 30.9일 |
| 재고 0 | 0 | — | — | — | — |

판매 변화는 관측값이다. 재고 위험·과잉은 가상 재고 규칙에서 나온 결과다. 판매가 빠르게 늘면 28일 평균 기반 발주가 뒤처져 소진 위험이 생기고, 최소 발주 30개와 여름 잔여 75일 기초재고는 과잉을 만든다. 실제 H&M 매장의 재고 상태가 아니다. 사례를 만들려고 판매나 재고를 조정하지 않았다.

## 8. 전수 검증 (`verify_hm_operating_case.py`, 실패 0건)

- **SKU:** 50종 모두 10자리 문자열이며 DB H&M 상품 ID와 정확히 일치한다.
- **첫 관측 판매일:** DB와 50종 모두 일치한다.
- **수불:** SKU마다 84일이 연속이다. 4,200행 모두 `공급 = min(관측, 기초+입고)`, `부족분 = 관측 − 공급`, `기말 = 기초 + 입고 − 공급`을 만족한다. 음수 재고 0건, 전날 기말 = 다음 날 기초, 8/31 이전 부족분 0건이다.
- **판매:** 4,200행 모두 DB 일별 판매(채널 합계, 기록 없는 날은 0)와 같다.
- **발주 ↔ 입고:** 89건 모두 발주일이 있고 8/31 이전이다. 상태는 `received`·`open`만 있다(사후 정합 입고 0건). 입고 합계가 수불 입고와 날짜별로 일치한다.
- **재발주 불가 13종:** 설정일 이후 발주가 0건이다.
- **가격:** 구간이 7/1~9/22를 공백·중복 없이 덮는다. 원가 < 판매가 ≤ 정가.
- **9월 정보 누출 검사:** 9월 판매를 지우고 다시 생성해도 선정 50종, 8/31까지의 수불, 모든 발주가 같다.

프로그램 쪽 검증은 `backend/tests/test_hm_simulation.py`에 있다. 가져오기 시 같은 검사를 서버에서 다시 수행하고, 하나라도 실패하면 아무것도 저장하지 않는다. 사후 정합 입고나 재발주 불가 설정일 이후 발주가 들어 있으면 거부한다.

### 생성 과정에서 바뀐 규칙 (공개)

1. v1 첫 실행에서 재발주 불가 여름 잔여 `0608007001`의 8/31 재고가 0개였다. 원인은 "8/31까지 음수만 아니면 된다"는 보정 규칙이었다. 그래서 재발주 불가 상품의 8/31 재고 하한을 추가했다. 이 규칙은 9월 실패를 본 뒤 추가한 것이다.
2. v1 검증기가 사후 정합 입고가 8월 발주 검토의 미입고 수량에 섞이는 누출을 찾았고, 이를 고쳤다.
3. v2에서 사후 정합 입고를 없애고 공급 가능 수량과 공급 부족분을 분리했다.

## 9. 한계

- H&M 자료만으로는 품절 때문에 실제 판매가 억제됐는지 알 수 없다. 판매 0개인 날이 수요가 없었는지 재고가 없었는지도 구분할 수 없다.
- 판단 화면의 두 조치안 비교에서 "30일 가용 수량"은 8/31 재고 + 30일 안에 도착하는 계획 입고 + (리드타임 ≤ 30일인 경우) 추가 매입이다. 입고 전에 재고가 먼저 떨어지는 날짜별 공백은 이 비교에 반영되지 않는다. 날짜별 공백은 수불 그래프와 이후 관측 표에서 확인해야 한다.
- 원가, 가격, 리드타임, 최소 발주량, 할인율은 상품 종류만 보고 정한 가정이다.
- 거래 한 행 = 판매 1개로 셌다. 반품·취소는 원본에 없어 넣지 않았다.
- DB 모집단 선정에 9월 판매가 반영돼 있다(4절 표본 편향).
